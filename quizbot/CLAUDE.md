# Quizbot app — design notes & generation commands

Workshop-friendly Django app: a signed-in user picks a topic, gets five
multiple-choice questions of increasing difficulty (1 → 5) generated by
OpenAI, and is scored at the end with a proficiency label.

## How this app was generated

From the repo root (inside the dev container):

```bash
# 1. Scaffold the Django app at the repo root (NOT inside project_config/).
python manage.py startapp quizbot

# 2. Add `openai` to requirements.txt and install it. NOTE: pin to 1.59.2 or
#    later — earlier 1.5x versions break with httpx>=0.28 (see Troubleshooting).
pip install --user 'openai==1.59.2'

# 3. Register "quizbot" in INSTALLED_APPS and set LOGIN_URL / LOGIN_REDIRECT_URL
#    / LOGOUT_REDIRECT_URL / OPENAI_API_KEY / OPENAI_MODEL in
#    project_config/settings.py. Include quizbot.urls and the auth login/logout
#    views from project_config/urls.py.

# 4. Create models, then make + apply migrations.
python manage.py makemigrations quizbot
python manage.py migrate

# 5. Generate the sample-users fixture (passwords need real hashes, so we
#    build the JSON via a one-off shell rather than editing it by hand):
python -c "
import django, os, json
os.environ.setdefault('DJANGO_SETTINGS_MODULE','project_config.settings')
django.setup()
from django.contrib.auth.hashers import make_password
users = [{
    'model': 'auth.user', 'pk': pk,
    'fields': {
        'password': make_password('quizbot123'),
        'last_login': None, 'is_superuser': False,
        'username': u, 'first_name': f, 'last_name': l,
        'email': f'{u}@example.com',
        'is_staff': False, 'is_active': True,
        'date_joined': '2026-05-13T00:00:00Z',
        'groups': [], 'user_permissions': [],
    }
} for pk, (u,f,l) in enumerate([('alice','Alice','Algebra'),('bob','Bob','Builder'),('carol','Carol','Curious')], start=2)]
with open('quizbot/fixtures/sample_users.json','w') as fh: json.dump(users, fh, indent=2)
"

# 6. Load sample users into the dev database.
python manage.py loaddata sample_users

# 7. Run the tests.
python manage.py test quizbot
```

## Running it locally

```bash
python manage.py runserver 0.0.0.0:8000
```

Then visit the forwarded port, sign in as `alice`, `bob`, or `carol`
(password `quizbot123` for all three), and start a quiz.

### Providing the OpenAI API key

Without a key, the app silently uses the deterministic stub generator
(correct answer is always `"A"`). To get real OpenAI questions, set
`OPENAI_API_KEY` via one of:

1. **Codespaces secret (recommended for the workshop).** GitHub → Settings →
   Codespaces → Secrets, scope it to this repo. Rebuild the codespace once
   so the new env var is picked up.
2. **A `.env` file** at the repo root (`.env` is already in `.gitignore`):
   ```
   OPENAI_API_KEY=sk-...
   ```
   `project_config/settings.py` calls `load_dotenv(BASE_DIR / ".env")` at
   import time via `python-dotenv` (already in `requirements.txt`). Note
   that `load_dotenv` does **not** override existing env vars, so values
   set in `.devcontainer/devcontainer.json` (`DATABASE_URL`, `DJANGO_DEBUG`,
   `ALLOWED_HOSTS_ALL`) always win — the `.env` only fills in the gaps.
3. **`export OPENAI_API_KEY=...`** in the shell before `runserver`. Works
   but doesn't survive new terminals.

Do **not** put the key in `.devcontainer/devcontainer.json` — that file is
committed to git, and `AGENTS.md` says not to touch it.

## Design choices

### Multiple choice (A/B/C/D), not free-text

OpenAI generates a question, four options, and the correct letter in a single
JSON response. The user picks a letter and we grade by string equality. This
avoids:

- A second LLM call to grade free-text answers (cost, latency, flakiness).
- The "is this answer close enough?" judgement call, which is hard to test.

Cost: questions are slightly more constrained than free-form Q&A.

### Difficulty == question order

Question N is generated at difficulty N (1–5). The prompt asks for "very easy"
through "expert-level" via a label table in `services.py::DIFFICULTY_LABELS`.

The user advances through all five questions regardless of whether they got
the previous one right. This is simpler than ramping/dropping difficulty
dynamically and gives every user a comparable score (out of 5). Score is
the count of correct answers; the proficiency label maps directly:

| Score | Label        |
| ----- | ------------ |
| 0–1   | Beginner     |
| 2     | Novice       |
| 3     | Intermediate |
| 4     | Advanced     |
| 5     | Expert       |

### OpenAI service with stub fallback

`quizbot/services.py::generate_question` is the single entry point.

- If `settings.OPENAI_API_KEY` is empty, OR the OpenAI call raises, we log
  and return a deterministic stub question whose correct answer is always
  `"A"`. This means the workshop works offline / without a key, and tests
  don't need to mock anything for the stub-mode unit tests.
- The OpenAI call uses `response_format={"type": "json_object"}` so we get
  parseable JSON back, and `_validate_payload` rejects malformed shapes
  (wrong keys, wrong letter) by raising `QuestionGenerationError`.
- The model defaults to `gpt-4o-mini` (cheap, fast, JSON-mode capable) and
  can be overridden with the `OPENAI_MODEL` env var.
- Previously-asked question texts are passed to the model in an
  "avoid repeating" clause, to reduce duplicates within a quiz.

### Tests don't hit OpenAI

`quizbot.tests.QuizFlowTests` patches `quizbot.views.generate_question` with
`fake_question`, which returns deterministic fixtures. That means:

- Tests are fast and deterministic (no network, no API key needed).
- The mock is patched at the **view import site** (`quizbot.views.generate_question`),
  not at `quizbot.services.generate_question`, because the view does
  `from .services import generate_question` — patching at the source
  module wouldn't reach the local binding.
- `fake_question` returns correct="A" on odd difficulties and "B" on even
  ones, so answering "A" every time gives a predictable 3/5 (Intermediate)
  in `test_full_flow_mixed_score`.

`StubServiceTests` tests the stub generator directly via `override_settings`,
and `_validate_payload`'s error paths via direct calls.

### URL and ownership model

- Routes: `/quizbot/`, `/quizbot/start/`, `/quizbot/<id>/`,
  `/quizbot/<id>/answer/`, `/quizbot/<id>/results/`.
- Every view uses `@login_required` and looks up quizzes with
  `get_object_or_404(Quiz, id=..., user=request.user)` so users can never see
  or post to another user's quiz — verified by
  `test_cannot_access_another_users_quiz` (expects 404, not 403, since the
  filtered queryset just won't find the row).

### Models

- `Quiz`: user, topic, created_at, completed_at. `completed_at IS NULL` ⇒
  in progress. Score and proficiency are computed properties, not stored
  columns, so they always reflect current question state.
- `Question`: quiz, order, difficulty, text, choices (JSONField with
  A/B/C/D keys), correct_answer (letter), user_answer (letter or ""),
  is_correct, explanation. `unique_together = ("quiz", "order")` prevents
  duplicate question orderings.

`user_answer = ""` is the sentinel for "not yet answered". I chose this over
nullable because querying `filter(user_answer="")` reads more naturally than
`filter(user_answer__isnull=True)` for the "next unanswered question" lookup.

### Templates

App-local under `quizbot/templates/quizbot/` plus the login template at
`quizbot/templates/registration/login.html` (Django's auth views look for
that exact path by convention). All templates extend `quizbot/base.html`
which carries the inline CSS — no separate stylesheet to keep the workshop
diff small.

## Things intentionally left out

- No JS framework or HTMX. Each question is a full POST → redirect.
- No quiz resume across days (it works, but isn't designed for long pauses —
  the question is already generated and persisted on the server).
- No rate limit on starting quizzes. Add one if cost is a concern.
- No retry/backoff on the OpenAI call beyond "fall back to stub on any
  exception". Adequate for a workshop, not for production.

## Troubleshooting

### "I set OPENAI_API_KEY but still get stub questions"

The `_call_openai` helper catches **any** `Exception` and falls back to the
stub. Two common causes:

1. **`openai` / `httpx` version mismatch.** `openai==1.54.0` (and earlier
   1.5x releases) construct their HTTP client with a `proxies=` kwarg that
   `httpx>=0.28` removed. The constructor raises `TypeError: Client.__init__()
   got an unexpected keyword argument 'proxies'`, which gets swallowed.
   Fix: pin `openai>=1.59.2` (already done in `requirements.txt`). To
   diagnose this class of failure in the future, run:
   ```bash
   python -c "
   import os; os.environ.setdefault('DJANGO_SETTINGS_MODULE','project_config.settings')
   import django; django.setup()
   from quizbot.services import _call_openai
   print(_call_openai('Test topic', 1, []))
   "
   ```
   That bypasses the `try/except` and prints the real traceback.

2. **The fallback used to be silent.** `project_config/settings.py` now
   configures a `quizbot` logger that writes WARNINGs to the console, so
   the next time `_call_openai` falls back you'll see
   `WARNING quizbot.services: OpenAI call failed, falling back to stub: ...`
   in the `runserver` output. If you don't see that line, the stub is being
   used because `OPENAI_API_KEY` is empty (check `settings.OPENAI_API_KEY`
   from `python manage.py shell`).

### Why was the fallback silent in the first place?

By default Django doesn't surface arbitrary app loggers to stdout. The
`generate_question` flow logs via `logger.warning(...)`, but with no
handler configured for the `quizbot` logger that record went nowhere.
The `LOGGING` block in `project_config/settings.py` adds a `StreamHandler`
for that logger so future failures are visible without re-running the
codepath under a debugger.
